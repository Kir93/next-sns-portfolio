# 고빈도 틱 붕괴 재현 스파이크 — 판정 기록

> **판정: 원 기준 no-go → 재정의 기준 go (2026-09-24).** 원 판정 기준인 interaction latency(INP-정렬 지표) p75 > 200ms는 조정한 조건 어디에서도 재현되지 않았다. 스펙 조건(`?feedSize=506`, 20Hz)에서는 틱이 없을 때와 구분되는 저하가 없었고, 피드를 생성기 상한인 2000장으로 늘렸을 때만 p75가 40ms에서 88–104ms로 올랐다. 이 문서는 원 판정과 그 근거를 기록한다. 판정 뒤 붕괴 기준은 절대 임계에서 같은 실행의 대조군 대비 상대 기준으로 재정의됐고, 그 기준으로는 N=2000에서 붕괴가 재현된다(아래 "재정의 기준 판정").

### 스파이크 코드

틱 엔진을 만들기 전에 판정하는 것이 목적이었으므로, 본 구현(task-2)이 만들 경로 가운데 가장 나쁜 형태만 최소로 재현했다.

- `?tick=Hz`가 있으면 MSW worker가 준비된 뒤 `setInterval(1000/Hz)`을 시작한다.
- 틱마다 query cache의 전체 포스트 중 30%(인덱스 `i % 100 < 30`)의 `views`를 +1 한다. 반영은 `setQueryData` 1회 안에서 대상 포스트마다 `useToggleLike`의 `mapPost`를 한 번씩 적용하는 방식이다. 따라서 틱당 비용은 O(대상 수 × 전체 포스트 수)이며, 스펙이 "의도된 병목"으로 지목한 경로다.
- 캐시에만 쓴다(MSW `feed` 모듈 미변이). 스파이크는 부하의 크기만 보면 되므로 진실 소스 단일화는 task-2 범위로 남겼다.
- 탭이 끝나면 틱을 멈춘 뒤 커밋 정착을 기다린다. 틱이 계속 커밋하면 하네스의 종료 조건(커밋 수가 연속 두 샘플 동일)이 성립하지 않기 때문이다.

계측을 두 가지 추가했다. 틱 콜백 안에서 동기 ingestion 시간을 `performance.now()`로 쟀고, long task의 주체를 가르기 위해 `PerformanceObserver('long-animation-frame')`의 script attribution을 invoker별로 합산했다.

### long task의 주체 (N=2000, 20Hz)

long-animation-frame script attribution을 invoker별로 합산한 값이다(회차별, ms).

| invoker                    | 1회   | 2회  | 3회   | 담는 것                                                                                                      |
| -------------------------- | ----- | ---- | ----- | ------------------------------------------------------------------------------------------------------------ |
| `TimerHandler:setInterval` | 9487  | 9383 | 12953 | 틱 콜백 — `mapPost` 반복 + `setQueryData` (ingestion)                                                        |
| `TimerHandler:setTimeout`  | 12929 | 9893 | 13344 | TanStack Query `notifyManager`의 기본 스케줄러(`setTimeout(0)`)가 여는 통지 태스크와 그 안의 React 동기 렌더 |

두 invoker가 거의 반씩 나눠 가진다(ingestion 비중 42–49%). 즉 long task는 ingestion 루프만의 문제도, React 렌더만의 문제도 아니다. 틱 1회가 **ingestion 태스크 1개와 통지·렌더 태스크 1개**를 만들고, 둘 다 N에 비례해 커진다. 틱이 없는 N=2000 대조군의 `setTimeout` 합은 283–492ms로 작아서 이 몫의 대부분이 틱 통지임을 보인다.

## 해석

1. **스펙 조건에서는 방어선이 부하를 흡수한다.** N=506에서는 명목 100Hz까지 올려도 long task가 사실상 0건이었고, interaction p75는 틱이 없을 때와 같은 16–24ms 구간(event timing 하한 근처)에 머물렀다. 틱당 ingestion이 5ms 안팎이고 React Compiler와 `content-visibility:auto`가 렌더를 작게 유지하므로, 50ms 넘는 태스크가 생기지 않는다. 스펙 Risks의 "의존성 a — 이미 흡수할 가능성"이 실측으로 확인된 것이다.
2. **명목 Hz와 실제 전달률이 다르다.** 4x throttle에서 명목 20Hz는 약 10/s, 60·100Hz도 20–24/s에서 포화했다. N=506의 "20Hz" 조건은 실제로 10Hz였고, 명목 60·100Hz가 실제 20Hz 근처를 대신 재현했다. 결론은 같다(붕괴 없음). 다만 이후 리포트는 명목 Hz가 아니라 **전달된 틱 수**를 함께 기록해야 한다.
3. **N=2000에서 먼저 무너지는 것은 interaction latency가 아니라 틱 처리량이다.** 메인 스레드가 포화되면서 명목 20Hz 중 5–6/s만 전달됐다(70–74%가 실행되지 못해, 표시값이 그만큼 뒤처진다). interaction p75는 대조군보다 2.2–2.6배 올랐지만(40 → 88–104ms), 사용자 탭은 포화된 태스크 사이로 계속 끼어들었다. 틱 태스크 하나가 40ms 안팎이라 input delay가 그 이상 커지지 않기 때문이다.
4. **판정 기준(p75 > 200ms)은 어느 조건에서도 넘지 못했다.** 조정 가능한 두 축 가운데 N은 생성기 상한(`MAX_FEED_SIZE = 2000`)에 도달했고, Hz는 올려도 이미 포화된 전달률을 더 밀어 올리지 못한다(N=506에서 100Hz가 23/s에 머묾). 대상 비율(30%)을 올리거나 throttle을 6x로 조이면 넘길 가능성은 있다. 하지만 그것은 스펙이 경계한 "붕괴 연출"이어서 이 스파이크에서는 하지 않았다.

## 판정 (원 기준)

**no-go** — 스펙 Success Criterion 1의 "최종 미재현" 분기에 해당한다. task-2 이후는 착수하지 않는다. 피벗 여부와 방향은 스펙 `--update`에서 사용자가 결정한다.

판정을 바꾸는 데 필요한 결정은 다음 중 하나다. 어느 쪽도 이 스파이크가 대신 고르지 않는다.

- **기준 재정의** — 절대 임계(200ms) 대신 대조군 대비 상대 저하(N=2000에서 p75 2.2–2.6배, long task 포화)나 틱 처리량 붕괴(전달률 25–30%)를 붕괴 정의로 삼고, N=2000을 고정 조건으로 이어 간다.
- **서사 전환** — "React 19 + Compiler + content-visibility가 506장 × 100Hz까지 흡수한다"는 방어선 한계 측정으로 바꾼다. 무너지는 지점(N≈2000)과 그때 먼저 무너지는 축(처리량)을 주장의 중심에 둔다.
- **부하 축 추가** — 대상 비율 또는 throttle을 조정 축으로 공식 추가한다. 이 경우 "연출" 의혹을 막기 위해 그 근거(실제 서비스의 갱신 밀도 등)가 먼저 있어야 한다.

### task-3 적용 순서에 대한 함의 (피벗 후 재사용 가능)

붕괴를 만드는 조건(N=2000)에서 long task는 ingestion과 통지·렌더가 반씩 차지했다. 코얼레싱은 두 몫을 모두 줄인다. 틱 여러 개를 프레임당 1회 커밋으로 모으면 통지·렌더 태스크 수가 줄고, 대상별 `mapPost` 반복을 한 번의 병합 패스로 바꾸면 ingestion도 O(k×N)에서 O(N+k)로 줄어든다. 반면 `scheduler.yield()`는 ingestion 루프만 쪼갤 수 있고, React 동기 렌더 몫에는 닿지 않는다. 따라서 이 프로파일은 **코얼레싱을 먼저, 분해를 그 위에** 두는 순서를 지지한다.

## 재정의 기준 판정 (2026-09-24)

no-go 뒤 피벗은 첫 번째 선택지인 **기준 재정의**로 정해졌다. 새 기준은 다음 두 가지다.

1. interaction p75가 틱 없는 대조군(N=2000·틱 off)의 2배 이상.
2. 틱 전달률이 무부하 틱 대조군(N=506·같은 명목 Hz)보다, 그 대조군의 회차 간 변동을 넘어 낮음.

전달률을 명목 Hz로 나누지 않는 이유는 위 해석 2와 같다. 4x throttle만으로 명목 20Hz가 약 10/s로 떨어지므로, 명목 대비 비율(이 문서의 "25–30%")에는 부하와 무관한 몫이 섞인다.

이 스파이크의 수치로 보면 (1)은 2.2–2.6배, (2)는 5.3–6.0/s 대 10.1–10.2/s로 두 기준 모두 충족한다(**go**). 정식 판정은 진실 소스를 단일화한 틱 엔진으로 다시 쟀다. 두 실행 모두 p75 32 → 80ms(2.5배), 전달률 10.7–11.0 → 6.0/s였다 — [00-baseline.md](00-baseline.md).

## 한계

- 조건당 3회라 methodology의 K=5보다 적다. 스파이크의 목적은 go/no-go 판정이며, 이 수치를 baseline으로 쓰지 않는다(정식 baseline은 진실 소스를 단일화한 엔진으로 다시 잰다).
- event timing은 16ms 하한과 8ms 양자화를 가진다. N=506 행의 p75는 그 하한 근처라 차이를 해석하지 않는다.
- long-animation-frame attribution은 invoker 단위다. `TimerHandler:setTimeout`에는 틱 통지 외의 타이머도 섞이며, 그 크기는 대조군 수치(283–492ms)로 가늠했다.
- 틱 전달률은 탭 구간 동안 콜백이 실행된 횟수를 경과 시간으로 나눈 값이다.

## 재현

스파이크 코드는 머지하지 않았다(일회성). 스파이크와 같은 조건은 이제 커밋된 틱 엔진과 하네스로 다시 잴 수 있다.

```bash
PERF_SCENARIO=high-frequency pnpm perf
```

엔진이 스파이크와 다른 점은 두 가지다. 첫째, 틱이 MSW `feed`를 먼저 변이하고 캐시가 그것을 따른다(진실 소스 단일화). 둘째, hot set을 인덱스 규칙(`i % 100 < 30`) 대신 seed PRNG로 30% 고른다. 틱당 ingestion은 N=2000에서 스파이크 39–45ms, 엔진 38–40ms로 같은 크기다. 이 시나리오에는 N=2000·틱 off, N=2000·20Hz, N=506·20Hz가 들어 있다. 스파이크의 명목 60·100Hz 조건과 LoAF script attribution은 포함하지 않는다.
