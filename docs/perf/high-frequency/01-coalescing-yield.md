# 01 — 코얼레싱과 분해: `?sched` 4모드 해부

> **결론.** 2000장·명목 20Hz 부하에서 탭의 interaction latency(INP-정렬 지표) p75를 가장 확실하게 줄인 것은 분해(`scheduler.yield`)였다. off의 72ms가 5회 모두 32ms로 내려갔다. 코얼레싱은 틱당 캐시 반영 비용을 약 8분의 1로 줄였지만(35.3ms → 4.6ms) 틱 처리량은 늘리지 못했다. 틱이 프레임보다 드물게 도착해 프레임 단위 병합이 거의 일어나지 않았기 때문이다. 두 축을 합친 both는 p75 40ms(32–48)로, off(72–88)와 범위가 겹치지 않았다.

before 기준선과 붕괴 기준은 [00-baseline.md](00-baseline.md)를 따른다. 이 문서의 모든 비교는 같은 실행 안의 조건끼리만 한다.

## 네 모드 — 두 축의 조합

`?sched`는 ingestion을 두 축으로 나눈다. 한 축씩 켜야 각 축의 기여를 따로 잴 수 있다.

|                                                                               | 분할 없음      | 5ms마다 `scheduler.yield()` |
| ----------------------------------------------------------------------------- | -------------- | --------------------------- |
| **틱마다 커밋** (변경 포스트마다 `mapPost`, O(변경 수 × 피드 크기))           | `off` (before) | `yield`                     |
| **프레임마다 커밋** (버퍼에 모아 rAF당 병합 패스 1회, O(피드 크기 + 변경 수)) | `raf`          | `both`                      |

- `yield`는 `off`와 같은 계산을 한다. 다른 점은 그 계산을 5ms 조각으로 나눠 조각 사이에 메인 스레드를 양보한다는 것뿐이다. 같은 입력에서 `off`와 같은 최종 캐시가 나오는지는 단위 테스트로 고정했다. 다만 양보하는 동안 도착한 틱은 포스트 id 버퍼에 모였다가 다음 조각 루프에서 한 번에 커밋된다(아래 "백그라운드 탭과 대기열"). 그래서 틱이 몰리면 `yield`도 병합 커밋을 하며, 이때는 "틱마다 커밋" 축이 순수하게 분리되지 않는다. 이 측정에서 `yield`의 병합 commit은 5회 모두 0건이라 틱마다 커밋한 것과 같게 동작했다.
- 양보하는 사이 다른 쓰기가 캐시를 바꿀 수 있다(탭의 낙관 갱신, 페이지 로드). 이때는 계산 결과로 덮어쓰지 않고, 바뀐 최신 캐시 위에 같은 변경을 다시 병합한다. 아래 표의 rebase가 그 횟수다.
- 분기는 `src/mocks/tick/applyTicks.ts`의 `createIngestor` 한 곳에만 있다.

## 측정 조건

[00-baseline.md](00-baseline.md)와 같다. production 빌드, Pixel 5 에뮬레이션, CDP CPU 4x, 조건마다 warm-up 1회 폐기 후 5회 측정, 좋아요 20탭(인덱스 40부터). 조건은 N=2000·틱 off 대조군과 N=2000·명목 20Hz × 네 모드다. 환경은 macOS 27.0 / Apple M1 Pro × 10(로컬)이고, 커밋은 `f1edff5`(미커밋 변경 없음), 측정일은 2026-09-26이다.

틱을 멈춘 뒤 ingestion이 idle이 될 때까지 기다렸다가 비용·commit을 읽는다. yield·both는 탭 직후에도 버퍼 처리나 양보 대기가 남아 있을 수 있어서, 그 몫까지 창 안에 넣기 위해서다. 창의 끝에서는 전달된 틱과 그 비용이 같은 틱 집합을 가리킨다(시작 경계의 오차는 한계 절 참조).

## 판정

| 기준                                              | 결과                            |
| ------------------------------------------------- | ------------------------------- |
| `both`의 p75가 `off`보다 회차 간 변동을 넘어 낮음 | ✅ 범위 비중첩 (32–48 vs 72–88) |

같은 커밋에서 하루 전에 잰 실행은 이 기준을 완전히 만족하지 못했다(한계 절 참조).

## 해석

1. **분해는 응답성을 절반 이하로 줄였고, 작업량은 그대로였다.** `yield`의 틱당 ingestion은 `off`와 같은 수준이었다(34.8 vs 35.3ms). 줄어든 것은 한 번에 메인 스레드를 붙잡는 시간이다. 35ms짜리 태스크가 5ms 조각으로 쪼개지자, 탭이 그 사이에 끼어들어 p75가 72ms에서 32ms로 내려갔다. 총 작업량이 같으므로 전달률도 크게 달라지지 않았다(6.6 vs 6.2/s, 범위가 6.5에서 맞닿음).
2. **코얼레싱은 ingestion을 줄였지만 처리량을 늘리지 못했다.** 병합 패스가 틱당 캐시 반영을 35ms 안팎에서 5ms 안팎으로 줄였다. 그런데 병합 commit은 회차당 0–2건이었다. 거의 모든 커밋이 틱 1건만 실었다는 뜻이다. 틱은 초당 6건 남짓 들어오고 프레임은 그보다 자주 돌므로, 한 프레임 안에 틱 두 개가 쌓일 일이 드물다. 틱당 커밋 수(약 1)가 줄지 않았으니 틱마다 뒤따르는 통지와 React 렌더도 줄지 않았다. 표에서 `raf`·`both`의 캐시 commit 총수가 `off`보다 적은 것은 병합 때문이 아니라 같은 탭 구간에 전달된 틱 자체가 적었기 때문이다(회차마다 캐시 commit이 전달 틱 수와 같거나 1–2건 적다). 전달률은 `off`와 같은 수준이었다(6.1·6.2 vs 6.2/s).
   - ingestion을 8분의 1로 줄여도 전달률이 오르지 않았다는 것은, 남은 비용이 캐시 쓰기 이후 단계(통지·렌더)에 있다는 뜻이다. [스파이크 판정](spike-verdict.md)의 long-animation-frame 분석에서도 통지·렌더 몫이 절반 이상이었다. 렌더 비용을 직접 재지는 않았으므로 이 부분은 두 관측에서 끌어낸 해석이다.
   - `raf`의 p75는 이 실행에서 32ms(32–72)였지만 한 회차(72ms)가 `off` 범위 하단에 닿았고, 같은 커밋의 이전 실행에서는 64ms(64–72)였다. ingestion이 짧아지면 탭이 끼어들 틈이 생기지만, 렌더가 그 틈을 다시 채우는 것으로 보인다. 견고한 효과로 주장하지 않는다.
3. **순서 가정은 실측으로 보정됐다.** 스파이크는 long task의 42–49%가 ingestion이라는 프로파일을 근거로 "코얼레싱을 먼저, 분해를 그 위에" 두었다. 코얼레싱이 ingestion과 렌더 몫을 모두 줄일 것이라 예상했기 때문이다. 실측에서는 병합이 일어나지 않아 렌더 몫이 줄지 않았고, latency를 가장 안정적으로 줄인 것은 분해 단독이었다. 예상이 틀린 이유는 틱과 프레임의 빈도 관계였다. 틱이 프레임보다 잦은 부하였다면 결과는 달랐을 것이다.

## 백그라운드 탭과 대기열

`raf`·`yield`·`both`는 틱을 포스트 id 기준으로 버퍼에 모은다. 같은 포스트의 틱은 하나로 합쳐지므로 버퍼 크기는 갱신 대상 포스트 수(피드의 30%)를 넘지 않는다. 탭이 백그라운드로 가서 rAF가 멈추거나 양보 중에 틱이 밀려도 대기열이 끝없이 자라지 않는다. 복귀하면 한 번의 커밋으로 비워진다. 커밋은 항상 서버(MSW 피드)의 최신 수치를 복사하므로, 틱을 합쳐도 값을 잃지 않는다. `off`는 동기 처리라 대기열이 없다.

## 브라우저 지원

`scheduler.yield()`는 Chrome·Edge 129, Firefox 142부터 지원되고 Safari·iOS Safari는 지원하지 않는다(MDN browser-compat-data `api.Scheduler.yield`, 2026-09-24 조회. MDN은 Baseline이 아닌 Limited availability로 분류한다). 기능 감지 후 미지원 환경에서는 양보 없이 이어서 실행한다. 폴리필은 들이지 않았다([ADR-003](../../decisions/ADR-003-dependency-weight-quality-metric.md)). 따라서 Safari에서 `yield`·`both`는 분할 효과가 없고, `both`는 `raf`와 같게 동작한다. 측정은 Chromium에서만 했다.

## 한계

- **같은 커밋의 이전 실행은 머신 부하로 흔들렸다.** 2026-09-25 `f1edff5`에서 잰 실행은 대조군 p75가 56ms(56–64), long task가 회차당 10–23건으로 이 실행(16–24ms, 1–5건)보다 높았다. 그 실행에서 `both`는 72ms(64–104)로 한 회차(104ms)가 `off`(96–120) 범위와 겹쳤고, `yield`와 `raf`는 64ms(64–72)였다. 다른 앱을 닫고 다시 쟀으며, 결과와 무관하게 다시 잰 실행을 채택하기로 미리 정했다. 계측을 고치기 전(작업 트리 상태)에 잰 수치는 싣지 않는다.
- 조건마다 5회라, 한 회차의 이상치가 범위 판정을 좌우한다.
- event timing은 16ms 하한과 8ms 양자화를 가진다.
- 측정 창을 여는 순간 이미 수신돼 처리 중이던 틱(수 건)은 전달 수에는 빠지고 비용·commit에는 들어갈 수 있다. 창 전체(수백 틱)에 비해 작아 틱당 수치를 바꾸지 않는다.
- `yield`·`both`의 틱당 ingestion은 조각별 실행 시간의 합이다. 양보하는 동안 다른 태스크가 쓴 시간은 들어가지 않는다.
- 카운터는 O(1) 증가와 `performance.now()` 쌍뿐이지만, 측정 대상과 같은 메인 스레드에서 돈다.

## 재현

```bash
PERF_SCENARIO=sched pnpm perf
```

production 빌드 후 조건 5개(N=2000 틱 off 대조군, 그리고 명목 20Hz의 `off` / `yield` / `raf` / `both`) × (warm-up 1 + 5회)를 한 실행 안에서 진행한다. 로컬 기준 약 24분이 걸린다. 요약의 "조건 비교" 표와 조건별 카운터 행(캐시 commit·병합 commit·rebase)을 위 표와 대조한다.
