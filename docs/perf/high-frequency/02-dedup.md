# 02 — 틱 스트림과 낙관 토글의 정합: 유실 업데이트 0

> **결론.** 틱이 쉬지 않고 카운트를 바꾸는 동안 좋아요를 연타하거나 요청이 실패해도, 최종 좋아요 상태와 카운트가 서버(MSW 피드)와 같게 끝나도록 병합 규칙을 세 줄로 정했다. 재설계 전 코드는 세 경합 시나리오를 모두 틀렸다. 틱이 낙관 +1을 지웠고, 연타 직후 화면이 마지막 탭의 의도를 보여주지 못했고, 실패 롤백이 그 사이의 틱을 지웠다. 재설계 후에는 세 시나리오의 단위 테스트와 브라우저 e2e가 모두 통과한다.

이 문서가 다루는 것은 정합이다. 좋아요 한 건의 반응 속도는 측정 대상이 아니며, 틱 부하 아래의 latency는 [01-coalescing-yield.md](01-coalescing-yield.md)를 본다.

## 경합이 생기는 이유

좋아요 토글은 낙관적으로 동작한다. 탭하면 캐시를 먼저 바꾸고, 서버 응답은 나중에 온다. 재설계 전 `useToggleLike`는 탭할 때 피드 캐시 전체를 스냅샷으로 떠 두고, 실패하면 그 스냅샷으로 되돌리고, 성공하면 응답의 카운트로 캐시를 덮어썼다. 요청이 진행 중인 동안 캐시를 바꾸는 주체가 사용자 자신뿐일 때는 이 방식이 맞다.

틱은 그 가정을 깬다. 틱은 쿼리가 아니라 캐시에 직접 쓰기 때문에 `cancelQueries`로 멈출 수 없다. 요청이 오가는 사이 같은 포스트나 다른 포스트의 카운트가 계속 바뀐다.

## 병합 규칙

1. **좋아요 여부(`liked`)는 사용자의 마지막 의도를 보여준다.** 요청은 포스트마다 한 번에 하나씩 순서대로 보낸다(TanStack Query mutation `scope`). 보낼 차례가 왔을 때 의도가 이미 서버와 같으면 보내지 않는다. 그래서 요청이 오가는 동안 들어온 탭은 몇 번이든 추가 요청 최대 1건으로 합쳐진다(짝수 번이면 0건).
2. **좋아요 수(`likes`)는 서버 값에 아직 반영되지 않은 내 의도의 ±1을 더한 값이다.** 틱을 캐시에 반영할 때 캐시의 `liked`와 서버의 `liked`가 다르면 그 차이만큼 ±1을 다시 얹는다.
3. **요청이 실패하면 내 ±1만 철회한다.** 피드 전체를 스냅샷으로 되돌리지 않으므로 그 사이 틱이 반영한 값은 남는다.

서버 응답의 카운트는 캐시에 다시 쓰지 않는다. 규칙 2 덕분에 캐시가 이미 응답과 같은 값을 갖고 있고, 서버가 요청을 처리한 뒤 틱이 한 번 더 왔다면 응답이 캐시보다 오래된 값이기 때문이다.

다만 요청이 오가는 사이 다른 쓰기(피드 refetch, 다른 mutation의 롤백)가 캐시의 `liked`를 이전 값으로 덮을 수 있다. 그래서 사용자 의도는 캐시와 별도로 기억해 두고, 의도와 서버 상태가 같아지면 캐시의 `liked`가 서버와 다를 때만 맞춰 둔다. 덮어쓴 쓰기가 없으면 이 보정은 아무것도 하지 않는다.

| 시나리오                                     | 좋아요 여부           | 좋아요 수                                      |
| -------------------------------------------- | --------------------- | ---------------------------------------------- |
| 요청 진행 중 틱 도착 (서버 처리 전)          | 내 의도               | 틱이 반영된 서버 값 + 내 ±1                    |
| 요청 진행 중 틱 도착 (서버 처리 후, 응답 전) | 내 의도 (서버와 같음) | 틱이 반영된 서버 값 (내 ±1은 이미 서버에 포함) |
| 요청 진행 중 추가 연타                       | 마지막 탭의 의도      | 서버 값 (추가 요청은 최대 1건)                 |
| 요청 진행 중 refetch가 `liked`를 덮음        | 끝나면 서버 상태      | 서버 값                                        |
| 요청 실패                                    | 서버 상태로 복귀      | 틱이 반영된 서버 값 (내 ±1만 철회)             |
| 피드 다음 페이지 fetch 완료                  | 내 의도               | 서버 값으로 재동기화 + 진행 중인 내 ±1         |

마지막 행은 [00-baseline.md](00-baseline.md) 작업의 리뷰에서 발견한 경합이다. 무한 스크롤의 다음 페이지 fetch가 끝나면 TanStack Query는 fetch를 시작한 시점의 페이지들에 새 페이지를 붙인다. 그 사이 틱이 앞 페이지에 쓴 카운트는 fetch 시작 시점 값으로 되돌아간다. 틱 모드에서는 fetch가 완료될 때마다 모든 포스트를 서버 기준으로 한 번 다시 맞춘다(O(피드 크기), fetch마다 1회). 좋아요 요청이 진행 중인 포스트는 사용자 의도와 그 ±1을 유지하고, 나머지 포스트는 `liked`까지 서버 값으로 맞춘다. 좋아요 요청과 경주한 fetch 응답이 모든 요청이 끝난 뒤 도착해 옛 `liked`를 싣고 온 경우도 여기서 바로잡힌다. `setQueryData`가 내는 success 이벤트는 `manual` 표시로 걸러낸다.

## 좋아요 버튼의 진행 중 비활성화 제거

재설계 전 좋아요 버튼은 요청이 끝날 때까지 비활성화됐다. 경합을 직렬화로 막는 방식이었지만, 사용자에게는 두 가지 비용이 있었다. 연타가 무시되어 마지막 의도가 반영되지 않았고, 탭할 때마다 버튼이 흐려졌다가 돌아왔다. 이제는 규칙 1이 직렬화와 중복 제거를 맡으므로 비활성화를 없앴다. 방금 작성해 서버 id가 아직 없는 카드의 좋아요 버튼만 계속 막는다.

## 검증

### 단위 테스트 — 실패 먼저 (vitest, jsdom)

좋아요 핸들러를 두 단계 관문으로 감쌌다. 테스트가 서버의 처리 시점과 응답 도착 시점을 각각 정한다. 핸들러는 실제 핸들러처럼 MSW 피드를 직접 바꾼다. 스펙은 fake timers를 적었지만, 순서를 타이머 대신 관문으로 고정하는 편이 결정적이라 관문을 썼다.

| 테스트                                                                   | 재설계 전 (실패 확인)                                                 | 재설계 후 |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------- | --------- |
| (a) 틱이 요청 전후로 카운트를 바꿔도 낙관 +1 유지, 최종값이 서버와 같음  | ✗ 서버 처리 전 틱 뒤 카운트가 기대 135 대신 134(낙관 +1 소실)         | ✓         |
| (b) 첫 요청이 오가는 동안 세 번 더 탭하면 요청은 2건(첫 탭 + 합쳐진 1건) | ✗ 네 번 탭한 직후 화면이 마지막 의도(원래 상태) 대신 반대 상태를 표시 | ✓         |
| (c) 실패 시 내 ±1만 철회, 틱이 반영한 +3 유지                            | ✗ 기대 3 대신 0(롤백이 틱을 지움)                                     | ✓         |

- (d) 요청 도중 refetch가 `liked`를 덮어도 끝나면 서버와 같음 — 재설계 1차안의 리뷰에서 발견한 회귀를 고정하는 테스트다. 응답을 캐시에 되쓰던 재설계 전 코드는 이 경우를 통과하고, 되쓰기를 뺀 1차안은 틀렸다. 의도를 따로 기억하고 수렴 시점에 보정하도록 고친 뒤 통과한다.
- (b)는 처음에 한 이벤트 안에서 두 번 호출해 "짝수 연타는 요청 0건"을 고정했다. 실제 탭은 이벤트가 따로라서 첫 탭의 요청이 먼저 출발한다. 그 주장은 실제 동작과 달랐으므로, 탭을 따로 보내는 지금의 형태로 바꿨다.
- 기존 `useToggleLike` 4건과 `PostActions` 4건은 그대로 통과한다. `useToggleLike`의 첫 테스트는 응답을 되쓰지 않는 지금의 동작에 맞게 이름만 "서버와 같은 상태로 끝난다"로 바꿨다(단언은 그대로).
- 페이지 fetch 후 재동기화는 `resyncFromServer` 단위 테스트 1건으로 고정했다. 진행 중인 낙관 좋아요의 ±1이 남는지도 함께 확인한다.

### e2e — 브라우저에서 최종 상태 (Playwright)

`/?tick=20`에서 카드 네 장을 각각 1·2·3·1번 탭하고(한 카드 안의 탭은 따로 된 클릭 이벤트), 1.5초 동안 틱이 계속 오게 둔 뒤 틱을 멈춘다. 그 뒤 네 카드의 좋아요 여부와 카운트 표시가 서버 응답과 같아지는지 확인한다. 중간 상태는 확인하지 않는다. 홀수 번 탭한 카드는 좋아요가 된 상태, 두 번 탭한 카드는 원래 상태로 끝나야 한다.

### 부수 효과 — 탭당 React 커밋

서버 응답을 캐시에 다시 쓰지 않게 되면서 탭당 React 커밋이 3건에서 2건으로 줄었다. 기본 `pnpm perf`(N=506·틱 없음)의 인터랙션 구간 커밋은 60에서 **40**이 됐고, 5회 전부 같았다. [methodology.md](../methodology.md)에 변경 시점을 적었다.

## 한계

- 규칙 2는 틱을 반영하는 쪽이 서버의 `liked`를 안다는 전제에 기댄다. 이 데모에서는 틱 엔진이 MSW 피드를 직접 읽으므로 성립한다. 실제 서비스의 시세성 스트림이 사용자별 좋아요 여부를 싣지 않는다면, 대기 중인 요청의 델타를 클라이언트가 따로 들고 있어야 한다.
- 요청은 포스트마다 직렬이다. 한 포스트를 연타하는 동안 요청 왕복만큼 서버 반영이 늦어진다. 화면은 탭마다 즉시 바뀐다.
- 실패하면 그 사이의 탭 의도까지 서버 상태로 되돌린다. 사용자는 다시 탭해야 한다.
- 틱이 없는 기본 모드에는 fetch 완료 재동기화가 없다. 게시물 작성 뒤의 전체 refetch 응답이 좋아요 요청보다 늦게 도착해 옛 `liked`를 싣고 오면 화면이 서버와 어긋날 수 있다. 이 경주는 재설계 전 코드에도 있었고 틱과는 무관해 이번 범위에서 다루지 않았다.
- 사용자 의도와 서버 확정 상태는 카드 컴포넌트 인스턴스가 들고 있다. 요청이 오가는 중에 카드가 다시 마운트되면 수렴 보정을 놓칠 수 있다. 피드는 id를 key로 쓰고 가상화를 하지 않아 이 경로는 드물다.
- 개발 서버 e2e 1건과 단위 테스트는 정합을 확인할 뿐, 경합이 얼마나 자주 일어나는지는 재지 않는다.

## 재현

```bash
pnpm test
pnpm test:e2e
pnpm perf
```

`pnpm test`에는 경합 단위 테스트(`app/_components/sns/SnsCard/useToggleLike.test.ts`의 "틱 스트림과의 경합")와 재동기화 테스트가 들어 있다. `pnpm test:e2e`에는 `e2e/like-tick-consistency.spec.ts`가 들어 있다. 탭당 커밋 수는 `pnpm perf` 요약의 "React commit (인터랙션)" 행에서 본다.
