# 00 — 고빈도 틱 baseline: 진실 소스 단일화 엔진의 붕괴 재현

> **결론.** 2000장 피드에 명목 20Hz 틱을 걸면 두 실행 모두 붕괴 기준을 충족했다. 좋아요 탭의 interaction latency(INP-정렬 지표) p75는 틱 없는 대조군 32ms에서 **80ms(2.5배)** 로 올랐고, 틱 전달률은 부하 없는 틱 대조군 10.7–11.0/s에서 **6.0/s** 로 떨어졌다. 틱 1회의 비용은 대부분 캐시 반영(ingestion, 39ms)에서 나왔고, 서버 측 feed 변이(2.2ms)는 작았다. 이 문서가 이후 리포트(01 코얼레싱·분해, 02 정합)의 before 기준선이다.

붕괴 기준은 [스파이크 판정](spike-verdict.md) 뒤에 다시 정했다. 절대 임계(p75 > 200ms)는 어떤 조건에서도 재현되지 않았기 때문이다. 대신 같은 실행 안의 대조군과 비교하는 상대 기준을 쓴다.

1. interaction p75가 **틱 없는 대조군**(N=2000·틱 off)의 2배 이상.
2. 틱 전달률이 **무부하 틱 대조군**(N=506·같은 명목 Hz — 붕괴가 없는 조건)보다, 그 대조군의 회차 간 변동을 넘어 낮음.

두 번째 기준을 명목 Hz로 나누지 않는 이유가 있다. CPU 4x throttle에서는 부하가 없어도 명목 20Hz가 약 11/s로만 전달된다(아래 N=506 행). 명목 대비 비율에는 throttle 자체의 지연이 섞여 부하 몫을 가를 수 없다.

## 부하 생성기 오버헤드 분리

두 층으로 나눠 기록한다.

| 구간                          | 담는 것                                                                     | N=2000 · 20Hz             | N=506 · 20Hz   |
| ----------------------------- | --------------------------------------------------------------------------- | ------------------------- | -------------- |
| 피드 생성 (로드 구간)         | `?feedSize` 생성기 + 초기 렌더. 첫 페인트에서 리셋되어 인터랙션 수치와 분리 | 참고값, 개선 주장에 안 씀 | 참고값         |
| 틱 서버 측 (`feedMs`)         | 틱을 MSW `feed` 객체에 반영 — 실제 서비스라면 서버가 치르는 비용            | 틱당 2.2–2.9ms            | 틱당 0.6–0.7ms |
| 틱 클라이언트 측 (`ingestMs`) | 캐시 반영 `setQueryData` — 이 슬라이스가 줄이려는 비용                      | 틱당 37.9–40ms            | 틱당 4.6–5.1ms |

N=2000에서 틱 비용의 93% 이상이 클라이언트 ingestion이다(N=506에서는 87–89%). 서버 측 비용은 생성기 오버헤드로 보고 개선 주장에서 뺀다. 틱 델타를 만드는 PRNG 호출(틱당 hot set 크기만큼)은 두 층 어디에도 계상하지 않았다. 틱당 수백 번의 산술이라 ms 단위에 드러나지 않는다.

## 해석

1. **N=2000에서 무너지는 원인은 ingestion 루프의 크기다.** 틱 1회가 캐시에 39ms를 쓰고, 그 뒤의 통지·React 렌더가 뒤따른다. 4x throttle 아래에서 이것이 초당 6번 반복되며 메인 스레드를 포화시킨다. 탭은 그 사이에 끼어들어 기다리고(p75 32 → 80ms), 틱은 제때 실행되지 못해 전달률이 무부하 대비 55% 수준으로 떨어진다. 스파이크에서 LoAF attribution으로 본 분할(ingestion 42–49%, 통지·렌더 나머지)과 방향이 같다.
2. **506장에서는 같은 틱이 흡수된다.** ingestion이 틱당 5ms라 long task가 거의 생기지 않고, p75도 대조군 수준(24ms)이다. 비용은 피드 크기에 비례하고, 문제가 되는 것은 O(변경 수 × 피드 크기) 구조다 — 변경 수(hot set 30%)도 피드 크기에 비례하므로 사실상 제곱에 가깝다.
3. **React 커밋은 최소 상태다.** 틱 없는 대조군은 두 실행 10회 전부 커밋 60이었다(기존 methodology의 30/30과 같음). 틱을 켜면 인터랙션 구간 커밋이 N=2000에서 334–341로 는다. 하네스는 탭 커밋과 틱 커밋을 따로 세지 않지만, 탭 구간(60초 안팎)에 전달된 틱이 365–394건이므로 늘어난 몫의 대부분은 틱 커밋이다(틱 1건당 커밋 1건 이하로 보면 설명된다). 컴파일러가 줄일 수 있는 리렌더 비용은 이미 줄어 있고, 남은 것은 **태스크 길이와 통지 빈도**다. 이것이 다음 리포트(코얼레싱·분해)가 겨냥하는 축이다.
4. **실행 간 일치.** 두 실행의 N=2000·20Hz p75 중앙값은 80ms로 같았고, 전달률도 6.0/s로 같았다. long task 건수는 104와 87로 흔들렸다(회차별 47–174건). methodology가 말하듯 이 지표의 노이즈는 "가끔 한 회차가 튄다"는 형태여서 중앙값만 본다.

## 한계

- **측정 시점 커밋이 `-dirty`다.** methodology는 dirty 수치를 공개 문서에 그대로 인용하지 말라고 정한다. 이 수치는 엔진·하네스를 커밋하기 직전의 작업 트리에서 나왔다. 커밋 후 같은 커맨드로 재측정해 해시를 교체하는 것이 원칙이며, 교체 전까지는 이 문단이 그 사실을 밝힌다.
- 무부하 틱 대조군(N=506)은 interaction 관측이 회차당 2–11건이라 p75가 비는 회차가 있다(실행 2의 2/5). 판정에는 이 조건의 p75를 쓰지 않고 전달률만 쓴다.
- 틱 전달률은 탭 구간(스크롤 시작 → 마지막 탭) 동안 실행된 틱 콜백 수를 페이지 시계로 잰 경과 시간으로 나눈 값이다. 틱은 첫 페인트 전부터 돌기 때문에, 로드 구간 long task(N=2000·20Hz 중앙값 4190·4257ms 대 틱 off 594·566ms — 위 비교 표 마지막 열)에 틱 비용이 섞인다. 그래서 로드 구간은 참고값으로만 둔다.
- 탭 뒤 틱을 멈추고 커밋 정착을 기다린다. 틱이 계속 커밋하면 하네스의 종료 조건(연속 두 샘플의 커밋 수 동일)이 성립하지 않기 때문이다. 탭 이후의 틱 비용은 측정에 들어가지 않는다.
- 절대값은 이 러너에 종속된다. 비교는 같은 실행 안의 조건끼리만 한다.

## 재현

```bash
pnpm install
PERF_SCENARIO=high-frequency pnpm perf
```

production 빌드 → 조건 3개(N=2000 틱 off / N=2000 20Hz / N=506 20Hz) × (warm-up 1 + 5회) 순서로 한 실행 안에서 진행된다. 요약은 `perf-results/summary.md`의 "조건 비교" 표에 나온다. 로컬 기준 한 실행에 약 12분이 걸린다(기본 시나리오는 약 1분). 그래서 CI와 기본 `pnpm perf`는 기존 단일 조건(N=506·틱 off)을 유지하고, 이 시나리오는 opt-in으로 분리했다. 데모 URL(`/?feedSize=2000&tick=20`)은 스트레스 모드에 들어가는 수단일 뿐이다. 앱은 첫 페이지 6장만 적재하므로, 방문자 화면에서 이 부하가 재현된다고 주장하지 않는다. 2000장을 한 번에 적재하는 것은 하네스의 요청 재작성이다.
