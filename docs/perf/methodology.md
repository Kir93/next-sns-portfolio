# 측정 방법론 — 재현 가능한 perf 하네스

> 이 문서의 모든 수치는 커밋된 코드로 재실행할 수 있다. `docs/perf/after.md`의 N=506 실험이 절차만 남고 스크립트가 커밋되지 않아 재현 불가였던 격차를 고치는 것이 이 하네스의 목적이며, KPI는 수치의 크기가 아니라 **수치의 재현 가능성**이다.

## 재현 방법

```bash
pnpm install
pnpm perf
```

fresh clone에서 이 두 명령이면 완주한다(macOS 검증). `pnpm perf`는 Playwright 브라우저 확인 → production 빌드 → K회 반복 측정 → 집계 순으로 진행하고, `perf-results/summary.md`(요약)와 `perf-results/*.json`(원시 수치)을 생성한다. 브라우저 설치를 러너가 직접 수행하는 이유는 `pnpm-workspace.yaml`의 `allowBuilds` 허용목록에 `@playwright/test`가 없어 `pnpm install`이 그 postinstall을 실행하지 않기 때문이다.

러너의 설치는 `--with-deps`를 붙이지 않으므로, 리눅스에서는 배포판에 따라 시스템 라이브러리를 한 번 채워야 할 수 있다 — `pnpm exec playwright install --with-deps chromium`. CI 워크플로가 이 단계를 따로 두는 것도 같은 이유다.

`perf-results/`는 gitignore 대상이며 실행 시작 시 비워진다 — 이전 회차의 JSON이 새 커밋 해시를 달고 재게시되는 것을 막기 위해서다. 리포트를 문서로 옮길 때는 커밋 해시와 함께 인용한다. 요약 헤더의 해시에 `-dirty`가 붙어 있으면 그 수치는 미커밋 코드에서 나온 것이므로 공개 문서에 그대로 인용하지 않는다.

## 산출 지표와 용어 규율

- **interaction latency (INP-정렬 지표)** — `PerformanceObserver('event')`의 interaction duration. 같은 `interactionId`의 이벤트(pointerdown/pointerup/click) 중 최댓값을 인터랙션 1건으로 집계한다(INP 자체의 산출 방식).
- **long task** — `PerformanceObserver('longtask')`의 건수/총합/최대.
- **React commit 카운트** — 초기 로드 구간과 인터랙션 구간을 분리해 집계.

공개 문서에서 **INP를 직접 주장하지 않는다.** INP는 페이지 수명 전체의 상위 백분위 필드 지표이고, 여기서 재는 것은 고정 시나리오의 랩 측정값이다. 표기는 항상 "interaction latency (INP-정렬 지표)".

## 부하 생성기 오버헤드 분리

스트레스 피드 생성(506개)은 MSW 핸들러 모듈이 최초 평가될 때 1회 실행된다. 그 비용이 인터랙션 수치에 섞이지 않도록 **첫 페인트를 경계로 관측 샘플을 리셋**하고, 두 구간을 따로 기록한다.

| 구간     | 필드                                             | 담는 것                                                    |
| -------- | ------------------------------------------------ | ---------------------------------------------------------- |
| 로드     | `commits.load`, `loadLongTask`                   | 피드 생성 + 초기 렌더. 참고용이며 개선 주장에 쓰지 않는다  |
| 인터랙션 | `commits.interaction`, `longTask`, `interaction` | 첫 페인트 이후 스크롤·탭 구간. 생성기 비용이 섞이지 않는다 |

경계 리셋은 형식적 장치가 아니다. 도입 전후 실측이 갈린다:

|                           | 리셋 전                          | 리셋 후                                     |
| ------------------------- | -------------------------------- | ------------------------------------------- |
| "인터랙션 구간" long task | 회차당 63–361 ms, 1–4건          | **10회차 중 8회 0건** (나머지 51 ms·145 ms) |
| 로드 구간 long task       | 인터랙션 값에 흡수돼 보이지 않음 | 회차당 69–221 ms, 1–2건                     |

즉 리셋 전에 인터랙션 지연으로 보고하던 long task는 **전부 피드 생성·초기 렌더의 것**이었다. 이 오염을 걷어내자 현 baseline의 인터랙션 구간에는 사실상 long task가 없다는 것이 드러났다 — 아래 분산 절과 유의성 임계가 그 위에서 다시 도출된다.

개선 주장은 인터랙션 구간 지표로만 한다.

## event timing의 구조적 한계

`PerformanceObserver('event')`의 `durationThreshold` 최솟값은 **16ms**이고 duration은 **8ms 단위로 양자화**된다. 즉 16ms 미만 인터랙션은 원천적으로 관측되지 않는다.

이 때문에 리포트의 `interaction.count`는 **시도한 탭 수가 아니라 하한을 넘은 관측 건수**다. 회차당 20회를 탭해 실측에서는 1–7건이 잡혔다. 표본이 4건 미만이면 `p75`를 숫자 대신 `null`로 낸다 — 1–2개 표본에서 뽑은 백분위수는 앱이 아니라 표본을 설명하기 때문이다. 같은 이유로 표본이 0건일 때 `max`도 `null`이며, 0ms로 기록하지 않는다.

## 하네스 자체의 분산

2026-08-09, darwin / arm64 / Apple M1 Pro × 10, Next 16.3.0, 위 고정 조건. **동일 커밋 5회 반복**이 `pnpm perf` 1회 실행의 단위이고, 그 실행을 같은 코드로 **2회** 반복했다. 아래 첫 표가 한 실행 안의 회차별 분산, 두 번째 표가 실행 간 분산이다.

> 구간 리셋과 warm-up을 넣기 전에 잰 수치는 폐기했다. 그 값들은 로드 구간 작업을 인터랙션 지연으로 계상하고 있었으므로, 여기 실린 숫자와 섞어 읽으면 안 된다.
>
> **측정 라벨: `5a0829c-dirty` — 하네스 자체가 아직 커밋되지 않은 상태의 기준선이다.** 위 재현 절이 "dirty 수치는 공개 문서에 인용하지 않는다"고 규정하므로, 이 절의 수치는 하네스를 커밋한 뒤 clean 해시로 재측정해 갱신해야 한다. 갱신 전까지는 후속 슬라이스의 before 값으로 확정 인용하지 않는다.

### 실행 간 비교

| 지표                             | 실행 1           | 실행 2           |
| -------------------------------- | ---------------- | ---------------- |
| React commit (초기 로드)         | 8 (CV 0%)        | 8 (CV 0%)        |
| React commit (인터랙션)          | **60 (CV 0%)**   | **60 (CV 0%)**   |
| 인터랙션 long task 총합 (중앙값) | 0 ms (CV 161.1%) | 0 ms (전 회차 0) |
| 인터랙션 long task 최대          | 71 ms (n=2)      | 데이터 없음      |
| interaction 관측 건수 (중앙값)   | 6 (CV 55.9%)     | 4 (CV 27.4%)     |
| interaction p75 (중앙값)         | 24 ms (n=3)      | 16 ms (n=3)      |
| 〔참고〕 로드 long task (중앙값) | 91 ms (CV 38.5%) | 75 ms (CV 62.7%) |
| cv:auto가 생략한 layout          | 406.3 ms         | 258.6 ms         |
| cv:auto가 생략한 style 재계산    | 86.6 ms          | 24.5 ms          |

**실행 간에 값까지 일치하는 것은 React commit 카운트뿐이다.** 구간 분리 이전 측정까지 합치면 4회 실행 × 5회 반복 = **20/20 회차 전부 `{load: 8, interaction: 60}`** 이었다.

나머지는 전부 흔들린다. 인터랙션 long task는 표본 자체가 거의 없어 중앙값이 0이고, 로드 구간은 실행 간 중앙값이 75 → 91ms, 실행 내 CV가 38–63%다. content-visibility 델타조차 layout 258.6 → 406.3ms(1.6배), style 재계산 24.5 → 86.6ms(3.5배)로 벌어졌다 — 이전 측정 3회에서 ±5%로 안정적으로 보였던 것은 표본이 적었기 때문이며, 이 실험은 각 실행에서 1회만 재므로 실행 내 분산을 알 수 없다.

> **`interaction max`가 16ms에 몰릴 때의 CV를 결정론으로 읽지 말 것.** 16ms는 관측 가능한 최솟값이므로, 낮은 CV는 "분산이 없다"가 아니라 "해상도 아래라 분산을 볼 수 없다"는 뜻이다. 이 경고는 생성되는 `summary.md`의 해석 한계 절에도 함께 출력된다.
>
> 러너가 빨라 전 회차 관측이 0건이 되면 두 행이 다르게 표시된다: `interaction max`는 값이 전부 `null`이라 **`데이터 없음`**, `interaction 관측 건수`는 값이 0으로 채워지므로 CV를 `0%`가 아니라 **`산출 불가(전 회차 0)`** 로 낸다. 어느 쪽도 "완전 결정론"으로 승격되지 않게 하려는 구분이다.

## 유의성 임계

**효과량이 하네스 노이즈를 넘을 때만 개선을 주장한다.** 비교를 두 종류로 나눠야 한다 — 위 실측이 보여주듯 둘의 노이즈가 다르다.

### 실행 간 비교 (before 커밋에서 한 번, after 커밋에서 한 번)

- **React commit 카운트만 유효하다.** 20/20 회차에서 값까지 동일했다(초기 로드 8, 인터랙션 60). 차이가 곧 효과이므로 1 차이도 유의하다. 단 모든 실행이 같은 머신이므로, 이 결정론은 아직 "같은 머신에서의 결정론"까지만 뒷받침한다.
- **나머지 지표는 실행 간 비교에 쓰지 않는다.** 코드 변경 없이 로드 long task 중앙값이 21%, content-visibility 델타가 1.6–3.5배 벌어졌다.

### 실행 내 A/B 비교 (한 세션에서 두 조건을 연달아 측정)

- **인터랙션 구간 long task는 현재 임계를 정의할 수 없다.** 10회차 중 8회가 0건이라 분산을 추정할 표본 자체가 없다. 0에서 0으로 가는 비교에는 백분율 임계가 성립하지 않는다 — 부하가 생겨 이 지표에 값이 실리기 시작하면 그때 임계를 산출한다.
- **interaction duration** — 관측 건수가 회차당 1–7건이고 값이 16–24ms(하한 근처)에 몰려 있다. p75가 산출되는 회차도 절반 남짓이다. 개선 주장에 쓰지 않는다.
- **로드 구간 long task** — 실행 내 CV 38–63%. 참고용이며, 이 슬라이스가 겨냥하는 것은 인터랙션 구간이라 개선 주장의 근거로 삼지 않는다.

> **지금 이 하네스로 "빨라졌다"고 말할 수 있는 지표는 React commit 카운트 하나뿐이다.** 나머지는 도구가 부정확해서가 아니라 잴 대상이 아직 없어서 비어 있다. 이 상태를 임계표에 그대로 남겨 두는 것이, 노이즈에 임의 임계를 씌워 개선을 주장할 수 있게 만드는 것보다 낫다.

### 후속 슬라이스에 대한 함의

이 표의 실질적 결론은 **before/after를 같은 실행 안에서 재야 한다**는 것이다. high-frequency-tick-inp의 `?sched=off|yield|raf|both` 4모드 비교는 한 세션에서 네 조건을 연달아 측정해야 유효하며, 커밋을 갈아가며 따로 잰 수치를 비교하면 commit 카운트 외에는 근거가 되지 않는다.

임계를 넘지 못한 차이는 "개선"이 아니라 "차이 없음"으로 기록한다.

### interaction 계열이 왜 이렇게 불안정한가

하네스 결함이 아니라 **아직 잴 부하가 없기 때문**이다. 현재 앱에는 고빈도 이벤트 소스가 없고, 좋아요 토글 1건은 React Compiler 메모와 `content-visibility:auto` 아래에서 대부분 16ms 하한을 넘지 않는다. 관측 건수가 회차당 1–7건으로 들쭉날쭉하고, 넘긴 건들도 하한값(16–24ms)에 붙어 있다. 같은 이유로 인터랙션 구간 long task는 10회차 중 8회가 0건이다.

이것은 **음성 결과이지 결측이 아니다.** 506장짜리 피드에 CPU를 4배 조인 상태에서 좋아요를 스무 번 눌러도 메인 스레드가 50ms 넘게 막히지 않는다는 관측이며, 그 자체가 다음 슬라이스의 출발점이다 — "리렌더는 이미 최소인데도 무엇이 무너지는가"를 물으려면 먼저 지금이 안 무너진다는 것이 측정돼 있어야 한다.

틱 엔진이 들어오면 인터랙션이 하한 위로 올라오고 이 축들이 유효해진다. 그 전까지 유효한 축은 commit 카운트다.

## React Profiler 커밋 카운트 — 채택

채택했고, `next build --profile`은 필요하지 않았다.

렌더러가 로드되기 전에 `__REACT_DEVTOOLS_GLOBAL_HOOK__` 스텁을 심으면 React가 거기에 renderer를 등록하고 커밋마다 `onCommitFiberRoot`를 호출한다 — React DevTools가 쓰는 것과 같은 경로다. 계측이 e2e 계층에만 있어 `<Profiler>` 래퍼가 앱 코드에 들어가지 않고, 일반 production 빌드에서 동작한다.

React Compiler와의 충돌도 없었다: 4회 실행 × 5회 반복, **20/20 회차 전부** `{load: 8, interaction: 60}`이었다(구간 분리·warm-up 도입 전후 모두 포함 — 이 축은 그 변경에 영향받지 않는다). 좋아요 20탭에 커밋 60건 — 탭당 3건이다. `useToggleLike`의 커밋 유발 지점은 `onMutate`의 낙관 `setQueryData`, mutation의 `isPending` 전이(좋아요 버튼 자기 비활성화), `onSuccess`의 서버값 `setQueryData`이며, 세 지점과 탭당 3건이 일치한다(개별 커밋을 원인별로 태깅해 계측하지는 않았다).

이 결정론은 **공짜로 얻어진 것이 아니다.** in-flight mutation이 끝나기 전에 집계하면 마지막 토글들의 `onSuccess` 커밋이 빠져 60이 47로 떨어진다(실측). 그래서 커밋 수가 연속 두 샘플 동일해질 때까지 — 즉 커밋 스트림이 멎을 때까지 — 기다린 뒤 집계한다. 이 종료 조건을 넣은 뒤의 4번째 실행에서도 5회 반복 전부 60이었다.

## after.md 교차 재현

`docs/perf/after.md`의 content-visibility 격리 실험을 본 하네스로 재수행했다(`e2e/perf/content-visibility.spec.ts`). 방법은 원 실험과 같다 — `cv:auto` 상태의 누적 렌더 카운터를 읽고, 모든 카드를 `content-visibility: visible !important`로 강제한 뒤 다시 읽어 차이를 본다. 두 판독 지점 모두 동일한 정착 대기를 거치므로 초기 렌더의 잔여 작업이 델타에 섞이지 않는다. 토글이 실제로 걸렸는지는 computed style로 확인한다.

| 지표                          | 원 실험 (2026-06-20, 비스로틀 시스템 Chrome) | 본 하네스 (2026-08-09, throttle 4x, 6회 측정) |
| ----------------------------- | -------------------------------------------- | --------------------------------------------- |
| cv:auto가 생략한 layout       | +42.9 ms                                     | **+250 ~ +406 ms**                            |
| cv:auto가 생략한 style 재계산 | +41.9 ms                                     | **+22 ~ +87 ms**                              |

**부호 일치** — 두 측정 모두 `cv:auto`가 off-screen 카드의 레이아웃·스타일 작업을 생략한다는 결론을 지지한다. 여섯 번의 측정 모두 크게 양수였다.

확인하는 것은 방향뿐이며 **배율은 해석하지 않는다.** 스로틀 유무·브라우저·피드 구성(`featured 6 + generated 500` 대 `gen-1..gen-506`)이 모두 다르고, 무엇보다 본 하네스의 측정치 자체가 코드 변경 없이 layout 1.6배·style 재계산 3.5배 범위로 흔들린다(각 실행에서 1회만 재기 때문에 실행 내 분산은 알 수도 없다). 원 실험과의 비율을 계산하는 것은 이 분산 위에서 의미가 없다.

## CI 편입 — report-only

CI는 perf 리포트를 아티팩트로 남길 뿐 **차단하지 않는다**. 임계값 게이트는 의도적으로 보류했다.

- 러너 환경(ubuntu 공유 러너)과 로컬(Apple Silicon)의 절대값이 다르고, 위 실측이 보여주듯 코드 변경 없이도 실행 간 지표가 크게 흔들린다. 이 상태에서 절대 임계로 차단하면 플레이크가 신호를 압도한다.
- 상대 비교 원칙상 의미 있는 비교 대상은 "같은 실행 안의 다른 조건"이며, CI가 단일 조건만 재는 현재 구성으로는 그 비교가 성립하지 않는다.

보류 판단 자체를 여기 기록해 두는 이유는, 게이트가 없는 상태가 누락이 아니라 결정임을 남기기 위해서다. perf job은 `continue-on-error`로 격리되어 있고, 공유 러너가 로컬보다 느린 것을 감안해 회차당 타임아웃 여유를 크게 잡았다. 요약 헤더에 러너 정보가 찍히므로 아티팩트만 보고도 어느 환경의 수치인지 판별할 수 있다.

perf job은 **main push에서만** 돈다(`if: github.event_name == 'push'`). `pull_request`에도 걸어두면 dependabot bump마다 3분짜리 측정이 아무도 읽지 않는 리포트를 위해 실행되고, 방법론이 인정하는 유일한 비교 대상 — main의 연속된 실행 — 에 브랜치 실행이 섞인다. 아티팩트 업로드에는 `if-no-files-found: error`를 걸어, 리포트를 만들지 못한 실행이 만든 실행과 같아 보이지 않게 했다(job 자체는 여전히 non-blocking).

**미검증 항목**: perf job은 아직 CI에서 한 번도 실행되지 않았다(로컬 실행만 검증). `continue-on-error: true`라 job이 죽어도 CI는 green으로 보이므로, main에 처음 push한 뒤 job이 완주하는지·아티팩트가 붙는지·실제 소요 시간이 얼마인지를 확인하고 그 값을 이 절에 적어야 한다.

## 리포트 규격

이후 성능 리포트(high-frequency 슬라이스 포함)는 이 8항목을 갖춘다. 코드 PR에 동반하며, 문서만 있는 독립 PR은 만들지 않는다.

1. 측정 환경 (기기·OS·러너)
2. 빌드 모드 명시 (production 여부)
3. 도구와 계측 방식
4. 수치 테이블 (중앙값 + 변동 계수 + 회차별 원시값)
5. 해석
6. 한계
7. 재현 커맨드
8. 측정 시점 커밋 해시 (dirty 여부 포함)

여기에 부하 생성기 오버헤드 분리 방법을 함께 적는다. 모든 수치는 실행 결과에서만 가져온다.
